# Measured distinction and bounded value hypothesis

Sources checked 2026-10-03: [incident.io post-mortem template](https://incident.io/hubs/post-mortem/incident-post-mortem-template), published 2025-04-16, describes incident summary/timeline, contributors, mitigators, learnings and follow-up actions; [official timeline editing page](https://docs.incident.io/incidents/edit-timeline) exists but retrieval exposed title/navigation only. The template encourages exploring contributors instead of fixing on a single cause. We credit this established workflow. Absence from these pages is not proof of missing incumbent capability. IncidentInterval has no claim of scientific novelty, world-first status, or winning a competitor benchmark.

Executed with `python examples/contrast.py` on synthetic JSON, compared with the documented local heuristic in `baseline.py`: blame the latest removable event whose point timestamp precedes impact. The heuristic is intentionally transparent, not incident.io code. A second ablation removes link evidence IDs; it tests whether the model still distinguishes conditional mathematics from source-supported action review.

| Executed case | Timestamp heuristic | Interval/structural result |
| --- | --- | --- |
| Skewed deployment clock, deploy hypothesis only | Rate limit | Rate limit has no guaranteed benefit; rollback conditionally prevents impact |
| Add load hypothesis | Rate limit | Rate limit and rollback each depend on which hypothesis holds; faster repair helps both |
| Trusted deployment time fixed at 20, after observed impact range | Rate limit | Deployment hypothesis contradicted; rate limit becomes a conditional candidate |
| Mechanism-source ablation | Rate limit | Faster repair needs mechanism evidence rather than becoming a recommended action |

The same executed fixture includes favorable faster repair (20s→5s, +15s modeled improvement), adverse slower repair (20s→30s, -10s), impossible repair with unchanged 20s measurement (INFEASIBLE), and recovery removal (unidentified duration). These contrasts are assertions about supplied hypotheses, not real customer results. Ground-truth cause and production savings are unknown. The baseline lacks uncertainty by construction; a high-quality manual SRE review may match or outperform this tool.

Specific user/buyer hypothesis: reliability engineers and service owners reviewing an incident remediation ticket when wall-clock order differs across hosts. The costly failure is selecting a follow-up from a false precise ordering, or ignoring an equally feasible explanation that recommends another action. The completed workflow imports documented JSON, emits evidence-bearing contradiction/critical-parent certificates, compares actions across explanations and highlights additional evidence needed. It can run locally beside an existing post-mortem document; it is not a new alerting/on-call platform.

A pilot could take 5–20 significant events with 2–4 hypotheses and reuse an incident's existing logs/clock-offset measurement. Setup requires manual modeling: if that costs 45 minutes and review saves only 15 minutes, the time case is negative. If reused schemas take 10 minutes to prepare and avoid a 30-minute re-review, the hypothetical net saving is 20 minutes per eligible incident. At an assumed internal labor cost C per hour and N eligible incidents, gross monthly time value would be `(20/60)*C*N`, before integration/support effort. C, N, eligibility, willingness to pay, adoption and revenue are not measured. No savings rate or price is claimed.

A credible support boundary is the versioned local SDK/CLI, exact bounded equations and reproducible certificates. Paid integration/support or a review-service wrapper is a possible business model, not an existing revenue stream. A pilot should measure preparation time, percentage of UNKNOWN/unsupported models, disagreements with independent SRE reviewers, changed follow-up decisions and whether proposed actions survive staging validation. Stop using the model for a decision when OR/feedback mechanisms dominate or source uncertainty cannot be bounded; returning UNKNOWN is part of the useful behavior.
